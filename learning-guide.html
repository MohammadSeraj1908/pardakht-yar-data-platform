How the platform works - simple learning guide

Read this once and you can explain the whole project.

1) The big flow (one line)

Simulator -> Source PostgreSQL -> Debezium -> Kafka -> Consumer -> raw -> Modeler -> report/marts -> Metabase

Remember: the 5 million initial rows are loaded directly into raw snapshots. Kafka carries only changes.

2) The story in 8 steps

1

Simulator creates data

It inserts 2,000 merchants and 5,000,000 transactions, then keeps changing the data (new transactions, status updates, reversals, risk changes, deletes).

2

Snapshot loader copies the 5M rows

It loads them directly into raw.transactions_snapshot. They do not go through Kafka.

3

Debezium reads the WAL

Debezium (inside Kafka Connect) reads every INSERT/UPDATE/DELETE from PostgreSQL and sends it to Kafka as JSON.

4

Kafka stores the changes

Two topics: pardakht.core.merchants and pardakht.core.transactions.

5

Kafka consumer writes raw events

It reads Kafka and inserts each change into raw.*_events with the Kafka offset (at-least-once).

6

Modeler builds the report

It reads only new events (watermark), keeps risk history (SCD2), and adds risk/province at transaction time.

7

Modeler refreshes the marts

Only the affected days/months/merchants are recomputed. Cards read these small tables.

8

Metabase shows dashboards

Two dashboards: the slow one on Core and the fast one on Warehouse.

4) The important code (file by file)

app/source_simulator.py

Creates the source data and changes it.


# 5 million rows in one INSERT
insert into core.transactions (...)
select nextval('core.txn_id_seq'), 1 + floor(random() * 2000)::bigint, ...
from generate_series(1, 5000000) g;

# every new transaction gets a unique id from a sequence
select nextval('core.txn_id_seq');

# schema change in the middle of the run
alter table core.transactions add column if not exists installments integer;

app/source_snapshot_loader.py

Bulk loads the initial rows (not through Kafka).


# server-side cursor reads the source in batches
with src.cursor(name="snap_transactions") as reader:
    reader.itersize = 20000
    reader.execute("select ... from core.transactions")
    rows = reader.fetchmany(20000)

# write each batch to the warehouse
execute_values(writer, "insert into raw.transactions_snapshot (...) values %s", rows)

app/warehouse_modeler.py

Builds report tables and marts, incrementally.


# 1) read only new events
select * from raw.transactions_events where event_id > %s order by event_id limit 5000;

# 2) risk at transaction time (SCD2 history)
left join lateral (
    select risk_level, province from report.merchant_history h
    where h.merchant_id = s.merchant_id and h.valid_from <= s.created_at
    order by h.valid_from desc limit 1
) h on true;

# 3) refresh only the affected groups
delete from report.mart_daily_sales m using ops.aff_daily k where m.day = k.day;

6) Glossary (simple words)

CDC

Change Data Capture: reading every change from a database.

LSN

Log Sequence Number: the position in the database log. It keeps changes in order.

Slot / publication

PostgreSQL objects that Debezium uses to read the WAL.

At-least-once

Every message is stored at least once; duplicates are removed by a unique key.

SCD2

Slowly Changing Dimension type 2: keep history using valid_from / valid_to.

Watermark

The last processed event id. It lets us read only new events.

Grain

What one row in a table means (for example: one transaction).

Mart

A small table that is already aggregated for a dashboard card.

Bulk snapshot

Load the initial data directly, not through Kafka.

7) Explain the project in 60 seconds

"I built a data platform for a payment company. A simulator fills a PostgreSQL source with 2,000 merchants and 5 million transactions. Debezium reads the database log and sends every change to Kafka. A small Python consumer stores those changes in a raw event table. A modeler then builds the report layer incrementally: it keeps merchant risk history as SCD2 and adds risk and province at transaction time. Five small marts power five Metabase cards. The benchmark shows the cards went from hundreds of milliseconds on the source to less than 10 milliseconds on the marts. Everything starts with one docker compose command and six end-to-end tests pass."

8) Commands to remember

docker compose up -d --build                  # start everything
docker compose ps -a                          # check containers
docker compose --profile test run --rm tests  # 6 E2E tests
docker compose --profile bench run --rm bench # write reports/runtime_report.md
docker compose down -v                        # full reset
